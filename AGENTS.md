# Dharana Web App — AGENTS.md

Веб-приложение Dharana (лендинг + каталог асан) на Next.js, общий бэкенд FastAPI. Краткий мануал для работы без вопросов.

## Стек и версии (важно!)
- **Next.js 15.5.25** (НЕ 16! create-next-app даёт 16.3.4, который ломает сборку на RSC: `(0, X.createContext) is not a function` в `next/navigation`. Не обновляться на 16 без острой нужды).
- React 19.2.8, Tailwind CSS v4 (config-less, токены — `@theme` в `app/globals.css`), TypeScript strict, i18next (один namespace `common`, ru/en).
- Сборка: `npm run build` (standalone). ESLint flat config: импорты `eslint-config-next/core-web-vitals.js` + `/typescript.js` (с расширением .js). Warn `nextVitals is not iterable` на сборке — безобиден.

## i18n (архитектура — ловушки)
- `lib/i18n/settings.ts` (locales/defaultLocale/isLocale), `lib/i18n/server.ts` (`getServerTranslation(locale)`), переводы `lib/i18n/locales/{ru,en}/common.json`.
- **НЕЛЬЗЯ импортировать `react-i18next` в Server Component**: тянет `createContext` из react-server-сборки → падение сборки. Server components используют чистый `createInstance` (без initReactI18next), текст со страницы SSR-ится.
- Для клиентских компонентов (формы Ф3+, интерактив) — отдельный клиентский инстанс с `initReactI18next` в **client**-boundary (ещё не сделан).
- i18next `resources` при init передавать ПОЛНОЙ вложенностью `{ru:{common:{...}}, en:{...}}`, а не `{common:{...}}` — иначе ключи не резолвятся (реальный баг, исправлен 2026-09-06).
- **Интерполяция**: серверный инстанс включает `interpolation: { prefix: "{", suffix: "}" }` (`lib/i18n/server.ts`) — `t("key", {var})` подставляет `{var}`. НО если строку с `{foo}` прогнать через `t()` БЕЗ передаваемой переменной, i18next вычистит плейсхолдер навсегда (сервер давно заSSR-ен, уже не поменять). Поэтому для ключей, которые интерполируются на КЛИЕНТЕ (`.replace(...)`) — использовать `%token%`, а не `{token}` (пример: timer.notifyAsana — «Асана: %name%»).

## Маршрутизация / локаль
- Страницы: `app/[locale]/page.tsx` (лендинг), статически prerender /ru и /en. Каталог/асаны/login/register — `export const dynamic = "force-dynamic"` (фетчатся на запрос), не кэшировать.
- `middleware.ts` — переадресация неизвестных путей на `/ru`. ВНИМАНИЕ: **в standalone-сборке middleware ИСПОЛНЯЕТСЯ** (проверено 2026-09-07: `/icon.svg` → 307 на `/ru/icon.svg`, пока не добавили его в matcher). Корневого `app/page.tsx` нет намеренно (Next требует root-layout, которого нет при `[locale]`-топ-левеле), поэтому редирект `https://dharana.ru/` → `/ru` дублирует Caddy (`redir @root /ru permanent`) — не мешает друг другу.
- **Matcher ОБЯЗАТЕЛЬНО исключает `api` и все корневые статик-ресурсы**: `"/((?!api|_next/static|_next/image|favicon.ico|icon.svg|robots.txt|sitemap.xml|download).*)"`. Иначе middleware заворачивает `/api/*` в `/ru/api/*` и ломает `app/icon.svg` (redirect `/icon.svg` → `/ru/icon.svg` → 404) — реальные баги, исправлены 2026-09-06 и 2026-09-07.
- Не создавать `app/page.tsx`/`app/layout.tsx` рядом с `app/[locale]` без согласования — сломает сборку.
- **Ловушка декодирования URL-сегментов (реальный баг 2026-09-07)**: под standalone-рантаймом с `NODE_ENV=production` (так деплоится прод — `ENV NODE_ENV=production HOSTNAME=0.0.0.0` в Dockerfile) Next отдаёт динамические `params` **percent-encoded**, а не декодированными (`/ru/asana/%D0%92...` → `params.name === "%D0%92..."`, а не «Вирасана»). Под `next start`/без NODE_ENV — декодирует нормально. Поэтому ВСЕ пути-параметры пропускать через `normalizePathParam()` (lib/api/catalog.ts: однократный `decodeURIComponent`, для декодированного значения no-op) перед использованием/`encodeURIComponent`. Основной пострадавший: страница `app/[locale]/asana/[name]/page.tsx` (карточки каталога вели на «Асана не найдена» на проде, локально работало — вот почему локальные тесты не ловили).
- Внутренние ссылки всегда с префиксом локали (`/{locale}/login`).

## Backend API (общий FastAPI)
- Base URL: `NEXT_PUBLIC_API_URL` (прод `https://api.dharana.ru`, dev `http://localhost:8000`), см. `lib/constants.ts`.
- **Все пути API идут через префикс `/api/v1`** (`API_PREFIX` в `lib/constants.ts`). Реальные URL: `/api/v1/auth/*`, `/api/v1/asanas`, `/api/v1/categories`, `/api/v1/media/photos/...`. lib/api/server.ts и mediaUrl() добавляют префикс сами.
- Aвторизация: `POST /api/v1/auth/register` (email/password/name) и `/api/v1/auth/login` → JWT bearer. JWT хранится в httpOnly-cookie `dharana_token`; браузер НЕ хранит токен — ходят через route handlers `app/api/auth/*` (login/register/logout/me), которые проксируют на API. 400 на register = email занят, 401 на login = неверные данные.
- Каталог (публичный): `/api/v1/categories`, `/api/v1/asanas` (`?category=&difficulty=&search=&limit=&offset=`), `/api/v1/asanas/{name}`. Поля: name, category_id, image_url (относительный `/api/v1/media/...` — клеить префикс API!), difficulty (1-5), effects[], contraindications[]. Ошибка приходит как 200 c `{"error": ...}` — проверять наличие `error`.
- `image_url` из API относительный — НЕ использовать как src напрямую, только через `mediaUrl()`.
- Бот: `@yogaasana_bot` → `https://t.me/yogaasana_bot`.
- Каталог/асаны/категории/комплексы — см. `dharana-api/app/routers/*` (там же детали премиум-гейтов и полей). Сверяться с контрактами перед реализацией Ф4+.

## Авторизация (логin/register/telegram) — добавлено 2026-09-08
- **Вход через Telegram** (веб-паритет приложения): кнопка на `/login` (`components/auth/telegram-login.tsx`) → модалка «Открыть бот» → `https://t.me/yogaasana_bot?start=auth` (бот зовёт `POST /auth/telegram/create-code`, получает код и присылает юзеру; код живёт 10 мин в `app_pending_telegram_auth`) → юзер вводит код → `POST /api/auth/telegram/verify` (`app/api/auth/telegram/verify/route.ts`) прокси-`{code}` на `/auth/telegram/verify`, ставит httpOnly-куку `dharana_token`. Клиент сам код получить НЕ может (он только у бота) — это by design.
- **Ошибки verify**: бэкенд `400 Invalid or expired code`/`400 Code expired`; route-handler мапит в ключи `auth.errorTelegramInvalid`/`auth.errorTelegramExpired` (клиент переводит по labels). Внимание: `create-code` — публичный endpoint (без авторизации), его можно дёргать для теста флоу (симуляция бота через curl), потом чистить тестового юзера в psql.
- **verify с кукой = привязка, без куки = вход**: route-handler `/api/auth/telegram/verify` передаёт `Authorization: Bearer` из `dharana_token`, если кука есть (с 2026-09-08). Бэкенд при наличии `current_user` делает merge bot-юзера в текущего (auth.py:226), иначе создаёт/возвращает TG-юзера. Поэтому тот же хендлер обслуживает и «Привязать Telegram» в профиле.

## Google OAuth (веб + Flutter) — добавлено 2026-09-09
- **Решение**: только Google (Apple недоступен), сразу «web + Flutter». Ссылка по email: существующий юзер получает `google_id`, `email_verified=true` (Google верифицировал).
- **Бэкенд**: `POST /auth/google` `{id_token, name?, avatar_url?}` → `{access_token, user}`. Валидация через **tokeninfo-эндпоинт** (`https://oauth2.googleapis.com/tokeninfo`), НЕ JWKS/PyJWT — ради этого в `requirements.txt` ОСТАЛИСЬ (неиспользуемые!) строки `PyJWT[crypto]>=2.8.0` и `cryptography>=43.0.0` (`app/services/google.py` — только httpx). Audience: `aud` или `azp` ∈ {`GOOGLE_CLIENT_ID` (web), `GOOGLE_ANDROID_CLIENT_ID` (Flutter-токены aud=android id, понятно)} — иначе 401 `INVALID_GOOGLE_TOKEN`. Конфиг без client id → 501 `GOOGLE_NOT_CONFIGURED`.
- **Модель/БД**: `User.google_id` (nullable, unique из приёмки google). **Миграция `c8d4e5f6a7b9`** — добавить `google_id` к `app_users`.
- **Веб**: `components/auth/google-login.tsx` — Google Identity Services, popup-флоу (`https://accounts.google.com/gsi/client`). Если `GOOGLE_CLIENT_ID` пуст — рендерит `null` (кнопка скрыта). `app/api/auth/google/route.ts` — серверный прокси `{id_token}` на `/auth/google`, ставит httpOnly `dharana_token` (тот же паттерн, что Telegram); 501/401 мапит в `googleFailed`/`googleNotConfigured`. `/login` — ОДИН разделитель `или` (`auth.or`) рендерится страницей ПОСЛЕ формы email/пароль; под ним стек кнопок Google+Telegram. Оба компонента принимают `hideDivider` (Google-проп всегда, Telegram — с 2026-09-09).
- **Ловушка ширины GSI-кнопки (баг 2026-09-09)**: `renderButton` по умолчанию рисует iframe ЕСТЕСТВЕННОЙ ширины (кнопка съезжает влево, в 2 раза уже контейнера; сразу после релоада виден полной-width плейсхолдер, затем сжатие). Фикс в `google-login.tsx`: мерить `btnRef.current.getBoundingClientRect().width` и передавать `width` в `renderButton`; `ResizeObserver` + rAF + guard `lastWidth` (>=1px) перерисовывают при изменении ширины. Кнопка всегда = ширине колонки `max-w-sm`.

## Профиль: аватарки и привязка Telegram (добавлено 2026-09-08)
- **Бэкенд** (`dharana-api/app/routers/profile.py`): `GET /profile/avatars` → `[{id,url,is_primary}]`; `POST /profile/avatars?url=`; `POST /profile/avatars/upload` (multipart **`file`**, ответ `{id,url,is_primary}`, ставит `user.avatar_url=url`); `DELETE /profile/avatars/{id}` (404 «Avatar not found», если primary — берёт первый оставшийся); `PUT /profile/avatars/{id}/primary`. Лимит **5** → 400 «Maximum 5 avatars allowed». URL файлов `/uploads/avatars/...` — StaticFiles `/uploads` на API (`app/main.py:100`), absolute через `mediaUrl()`.
- **Веб-слой**: серверный `getProfileAvatars()` (lib/api/user.ts); мутации — route-handlers `app/api/profile/avatars/upload|[/id]|[/id]/primary` через `lib/api/profile-actions.ts` (bearer из куки). 400 лимита мапается в `error: avatar_limit`.
- **UI**: `components/profile/avatar-picker.tsx` (`ProfileAvatar` — большая аватарка + кнопка-камера + бейдж-счётчик, модалка со списком/удалением/загрузкой; после мутаций `router.refresh()`) и `components/profile/link-telegram.tsx` (пункт-карточка «Привязать Telegram» виден только при `telegram_id == null`). Лейблы — `profile.avatar*`, `profile.linkTelegram*`, шаги/подписи модалки переиспользуют `auth.telegram*`.
- **Ограничения (как в приложении)**: primary-примёр не вызывается из UI (смена primary — только удалением); после DELETE primary бэкенд НЕ обновляет `user.avatar_url` (может остаться мёртвая ссылка — известно, идентично Flutter).
- **Ловушка локального `next start` для e2e частично-ручного**: `set VAR=value && cmd` в cmd.exe добавляет ПРОБЕЛ в значение (`API_URL="https://api.dharana.ru "`) → `ERR_INVALID_URL`. Env ставить через `$env:VAR=...` в том же PowerShell, затем `Start-Process` (наследует окружение). Профиль требует валидной куки (Secure-кука к http-локальному серверу curl всё равно отправит); для регистрации email должен проходить deliverability-проверку прода (gmail-подобные ок, `@example.com` отклоняется).

## Email-верификация при регистрации (ненавязчивая) — добавлено 2026-09-08
- **Смысл**: человек регается по почте, его сразу пускают в приложение. В профиле при `email_verified=false` показывается отключаемый баннер «Почта не верифицирована» + кнопка «Отправить ещё раз». Пригодится для восстановления профиля.
- **Почта — SMTP.BZ** (`app/services/email_service.py`): `POST https://api.smtp.bz/v1/smtp/send`, multipart-поля `from/name/subject/to/html`, заголовок `Authorization: <API_SMPT>`. Ключ — в `API_SMPT` (config.py), From — `SMTPBZ_FROM` (noreply@dharana.ru). **Fail-open**: без `API_SMPT` или при ошибке отправка молча логируется и НЕ роняет регистрацию/ресенд. Фоновый запуск через `send_verification_email_async` (task без GC-глушения).
- **Бэкенд-эндпоинты** (`dharana-api/app/routers/auth.py`):
  - `POST /auth/register` — после создания юзера `create_email_verify_token(user.id, email)` + фоновая отправка. Токен = JWT `{purpose:"verify_email", email, sub, exp 48ч}`, секрет JWT_SECRET.
  - `GET /auth/verify-email?token=` — публичный, идемпотентный; матчит user по id+email (email-замок из токена); ставит `email_verified=true`. Ошибка → 400 `INVALID_VERIFICATION_TOKEN`.
  - `POST /auth/verify-email/send` — для «Отправить ещё раз», требует авторизации; rate-limit **1/мин** (по `user.email_verify_sent_at`) → 429 `TOO_FREQUENT`. Ответ `{ok, sent}` (sent=false если ключ не настроен).
- **Модель/БД**: `User.email_verified` (bool, default false) + `User.email_verify_sent_at` — обычно в `/profile` и `/auth/me` (`email_verified`). Alembic:**миграция `b7c3e9f1a2d4`** (добавляет обе колонки; server_default false для существующих рядов).
- **Веб-слой**:
  - `components/profile/email-verify-banner.tsx` («use client») — баннер, рендерится в `profile/page.tsx` при `profile.email && !profile.email_verified`; кнопка resend → `POST /api/profile/verify-email/send` (route-handler `app/api/profile/verify-email/send/route.ts` → backend с bearer из куки); 429 мапается в `frequency`; баннер отключается через localStorage `dharana:emailVerifyDismissed`.

## Почтовый сервер (Postfix+Dovecot, self-hosted) — добавлено 2026-09-08
- **Стек**: `/opt/dharana/mail/` — отдельный docker-compose (сервис `mail`, контейнер `dharana-mail`, образ alpine:3.20 + postfix + dovecot + dovecot-lmtpd). Порты 25/143/993, named volume `mail_vmail`, сеть `dharana-mail`. Ящик `support@dharana.ru`, пароль — `/opt/dharana/mail/.env` (`MAIL_PASSWORD=...`, chmod 600 root). Maildir `/var/mail/vmail/dharana.ru/support/Maildir` (uid/gid 5000).
- **TLS**: `mail.dharana.ru` в `/opt/dharana/Caddyfile` (LE-сертификат у caddy, авто-продление). Файлы скопированы в `/opt/dharana/mail/tls/` (`mail.dharana.ru.crt` + `mail.dharana.ru.key`) при перевыпуске — ручная синхронизация НЕ нужна, пока не сменится cert (после реквеста нового можно `docker cp` заново из `/data/caddy/.../mail.dharana.ru/`).
- **DNS**: MX dharana.ru → mail.dharana.ru (pref 10/20), A mail.dharana.ru = 212.192.22.6, SPF `v=spf1 a mx include:spf.smtp.bz ~all`. PTR отсутствует (для входящих некритично).
- **Ловушки конфигурации (реальные баги при развёртывании)**:
  - `virtual_mailbox_maps` — ТОЛЬКО `lmdb:/etc/postfix/vmailbox` (в alpine-пакете postfix нет модуля `hash:`; `hash:` молча не открывает — «error: open database /etc/postfix/vmailbox.db: No such file` → 451). `postmap` в entrypoint создаёт `vmailbox.lmdb`, не `.db`.
  - `mydestination` — НЕ включать `$mydomain`: `mydestination = $myhostname, localhost.$mydomain, localhost`. Иначе письмо на `user@dharana.ru` трактуется как ЛОКАЛЬНОЕ (не virtual) → попытка поиска в aliases → «alias database unavailable» → 451 навсегда.
  - RHS строки `vmailbox`: `support@dharana.ru dharana.ru/support/Maildir/` — постфиксный virtual виртуал трактует RHS с `/` как КОРЕНЬ Maildir (массив `Maildir/`). Должно совпадать с dovecot `mail_location = maildir:/var/mail/vmail/%d/%n/Maildir`. Postfix кладёт письмо прямо в этот каталог (без dovecot-подселектов) — Maildir с подпапками создаёт сам.
  - `master.cf` — у `smtp`/`submission` chroot=`n` (иначе postfix не найдёт никакие файлы/БД в chroot).
  - Пользователь vmail: только числовые uid/gid (5000:5000), системного юзера в контейнере нет. `chown 5000:5000` + `chmod 700` в Dockerfile.
  - entrypoint: `mkdir -p $VMAILDIR/cur $VMAILDIR/new $VMAILDIR/tmp` КАЖДЫМ словом (brace-list `/{cur,new,tmp}` не раскрывается в POSIX-sh → создаёт каталог с AC-лицом *`{cur,new,tmp}`*), затем `postmap /etc/postfix/vmailbox` + `postalias /etc/postfix/aliases`.
  - Dovecot namespace-блоки: блоки `mailbox ... {` писать НА ОТДЕЛЬНЫХ СТРОКАХ (однострочная нотация «Garbage after '{'» → конфиг не читается, но dovecot стартует «молча»? нет — падает на syntax).
- **Проверка/сервис**: пересборка `sudo docker compose -f /opt/dharana/mail/docker-compose.yml up -d --build`; логи `sudo docker logs -f dharana-mail`; письма `sudo ls /var/lib/docker/volumes/mail_vmail/_data/dharana.ru/support/Maildir/new|cur`; посмотреть очередь `sudo docker exec dharana-mail postqueue -p`.
- **TTL писем 14 дней** (root cron, на хосте): `find /var/lib/docker/volumes/mail_vmail/_data -type f \( -path '*/Maildir/new/*' -o -path '*/Maildir/cur/*' \) -mtime +14 -delete` (ежедневно 04:30) + чистка `Maildir/tmp` старше 1 дня (04:40).
- **⚠ НЕ РАБОТАЕТ ИЗ INTERNET**: порты 25/143/993 блокируются на edge-фаерволе провайдера (с хоста через публичный IP — reachable; извне, включая локальную машину — BLOCKED; исходящий 993 с той же машины наружу — OPEN ⇒ блок не у ISP, а у провайдера VPS). ufw внутри открыт, docker DNAT есть. Требуется открыть порты в панели/тикете провайдера. До этого MX-приём внешних писем невозможен.
